# AGENTS.md

Guidance for humans and coding agents working on **flutter_brainflow**, a Flutter
plugin that exposes [BrainFlow](https://brainflow.org) (biosensor data acquisition
and processing) to Dart/Flutter apps.

> Status: greenfield. The structure and plan below are the target; update this
> file when reality diverges from it.

## Goals and non-goals

**Goals**
- Idiomatic Dart API over BrainFlow's C API: `BoardShim`, `DataFilter`, `MLModel`.
- Stay close to BrainFlow's official bindings (Python/Java) in naming and
  semantics, so BrainFlow docs and examples transfer directly.
- Async, UI-friendly layer on top (connect without janking, `Stream` of data).
- Platforms: **Linux** and **Android** first (the devcontainer supports both);
  macOS/Windows later, as they mostly come for free with prebuilt libs.

**Non-goals**
- Re-implementing BrainFlow logic in Dart. We wrap; we do not port.
- Shipping our own device drivers or BLE stack.
- Enterprise layering. Prefer a few clear files over many tiny abstractions.

## Key design decisions

1. **`dart:ffi` against the C API, bindings generated by `ffigen`.**
   BrainFlow already exposes a flat C API (`board_controller.h`,
   `board_info_getter.h`, `data_handler.h`, `ml_module.h`). No platform channels,
   no Kotlin/C++ glue code of our own.
2. **Native libraries delivered via Dart build hooks (`hook/build.dart`, native
   assets),** built from the pinned BrainFlow release artifacts (verified in M0):
   - Linux/macOS/Windows: `compiled_libs.tar` (118 MB, all desktop OSes mixed).
   - Android: `jni/<abi>/*.so` from `brainflow-android.aar` (100 MB).
   - Override via **pubspec user-defines**, not env vars (hooks strip env vars):
     `hooks: user_defines: flutter_brainflow: lib_dir: <path>` in the *app's*
     (workspace root) pubspec.
   The BrainFlow version is pinned in exactly **one** place
   (`hook/brainflow_version.dart`) and must match the vendored headers.
3. **Android needs a small `android/` Gradle part as well:** SimpleBLE's
   Java bridge classes (`libs/simpleble-bridge.jar` in the AAR) must end up in
   the APK, which a build hook cannot do. minSdk is **31** (BrainFlow's AAR
   requires it). No Kotlin plugin code needed so far.
4. **Two API layers:**
   - `BoardShim` (sync, 1:1 with BrainFlow): thin, predictable, easy to diff
     against the Python binding.
   - `BoardSession` (async, Flutter-friendly): runs slow calls (`prepare_session`
     may take seconds for BLE) via `Isolate.run`, polls data on a timer and
     exposes `Stream<BoardData>`. BrainFlow keeps session state process-global,
     so any isolate can call into the same session.
5. **Errors are exceptions.** Every native call goes through one helper that
   turns non-zero exit codes into `BrainFlowException(BrainFlowExitCode)`.
6. **Native memory never leaks into the public API.** Public types use
   `Float64List`, `List<int>`, Dart enums and plain classes. `Pointer`s stay
   inside `lib/src/ffi/`.

## Package layout

```
flutter_brainflow/
├── AGENTS.md
├── pubspec.yaml
├── ffigen.yaml                  # one config per header group is fine
├── hook/
│   ├── build.dart               # downloads/locates libs, registers CodeAssets
│   └── brainflow_version.dart   # single source of truth for the version
├── android/                     # Gradle only: simpleble-bridge.jar, minSdk 31
├── third_party/brainflow/include/  # vendored headers for the pinned version
├── lib/
│   ├── flutter_brainflow.dart   # public exports only
│   └── src/
│       ├── ffi/                 # the ONLY place that imports dart:ffi
│       │   ├── bindings.g.dart  # generated, never edit by hand
│       │   └── native_utils.dart# string/array marshalling, checkExitCode()
│       ├── core/                # pure Dart, no FFI: easy to unit test
│       │   ├── board_ids.dart
│       │   ├── exit_codes.dart  # BrainFlowExitCode + BrainFlowException
│       │   ├── input_params.dart# BrainFlowInputParams -> JSON
│       │   ├── presets.dart, log_levels.dart
│       │   ├── board_description.dart  # parsed get_board_descr JSON
│       │   └── board_data.dart  # row-major matrix + channel accessors
│       ├── board/
│       │   ├── board_shim.dart  # sync wrapper
│       │   └── board_session.dart # async + Stream layer
│       ├── data_filter/         # DataFilter + its enums
│       └── ml/                  # MLModel + its enums
├── test/
│   ├── unit/                    # pure Dart, no native libs
│   └── native/                  # real libs, SYNTHETIC_BOARD / PLAYBACK_FILE_BOARD
├── example/                     # Flutter app: connect, live plot, band powers
└── tool/
    ├── update_brainflow.sh      # bump version: headers + hook + regen bindings
    └── ...
```

Dependency direction: `board/`, `data_filter/`, `ml/` → `ffi/` + `core/`.
`core/` depends on nothing. Nothing depends on `board_session.dart` except the
public export.

## Conventions

- Follow `package:lints/recommended` (or `flutter_lints`); `dart format` clean.
- Naming mirrors BrainFlow but in Dart style: `get_board_data` → `getBoardData`,
  `BoardIds.SYNTHETIC_BOARD` → `BoardIds.syntheticBoard`. Keep the BrainFlow
  integer value on each enum (`final int value`).
- Doc comments on every public member; link the BrainFlow docs where useful.
- `bindings.g.dart` and other `*.g.dart` files are generated: regenerate, don't edit.
- Allocate with `using((arena) { ... })` from `package:ffi`; no manual `free`
  scattered around.
- Do not add a dependency for something that is ~20 lines of code.
- Keep the public API small. Adding a public symbol is a deliberate decision;
  export it in `lib/flutter_brainflow.dart`.
- Practical SOLID: one responsibility per file/class, depend on `core/` types
  rather than FFI types, and introduce an interface only when there is a second
  implementation (e.g. a fake for app-level tests), not "just in case".

## Commands

```sh
flutter pub get
dart run ffigen --config ffigen.yaml     # regenerate bindings
dart format .
flutter analyze
flutter test test/unit                   # fast, no native libs needed
flutter test test/native                 # needs BrainFlow libs (hook download or lib_dir user-define)
cd example && flutter run -d linux       # or an Android device via adb
```

Before finishing any change: format, analyze with zero issues, run unit tests,
and run native tests if you touched `ffi/`, `board/`, `data_filter/`, `ml/` or
`hook/`.

## Testing strategy

- **Unit tests** (`test/unit`): JSON of `BrainFlowInputParams`, parsing of board
  descriptions, `BoardData` indexing, exit-code mapping. No native code.
- **Native tests** (`test/native`): exercise the real library with
  `BoardIds.syntheticBoard` (no hardware) and `playbackFileBoard` (deterministic
  replays from `test/fixtures/`). Every wrapped native function needs at least
  one test here.
- **Hardware**: manual, documented in the example app's README. Never required
  for CI.

## Gotchas

- `libBoardController` finds its own directory (`dladdr`) and dlopens
  board-specific helper libraries from there (`libsimpleble-c.so`,
  `libMuseLib.so`, `libGanglionLib.so`, ...). Every helper is registered as a
  `CodeAsset` (with an unused asset name like `helper/muse`) purely so it gets
  bundled next to it. Verified: `dart run` puts them in `.dart_tool/lib/`,
  Flutter Linux in `bundle/lib/`, Android in `lib/<abi>/`.
- Linux runtime deps of helpers: `libdbus-1.so.3` (SimpleBLE/BlueZ) and
  `libbluetooth.so.3` (classic Bluetooth). Document for app developers.
- `compiled_libs.tar` has Linux **x64 only** (no Linux arm64 prebuilt).
- Android: `libBoardController.so` hard-links `libsimpleble-c.so`, which
  imports `JNI_GetCreatedJavaVMs@LIBNATIVEHELPER_S`, so it **cannot load below
  API 31** and finds the JavaVM itself. `java_set_jnienv` is therefore not
  needed (the Java binding calls it, but on Android it only forwards the VM to
  SimpleBLE). Unverified on a device: whether SimpleBLE can find the bridge
  classes from a Flutter app. If not, call `simpleble_android_set_jvm` or
  `java_set_jnienv` from a tiny Kotlin/JNI shim.
- Android AAR libs are unstripped (114 MB per ABI); AGP strips them to ~5 MB
  when packaging, so the hook does not need to strip. Skip `libjnidispatch.so`
  (that's JNA for the Java binding).
- **`prepare_session` rejects partial JSON**: `BrainFlowInputParams` must
  always serialize all 16 fields (`master_board` defaults to `-100`,
  `NO_BOARD`), like the Python binding. `{}` fails with exit code 17.
- **Isolates:** a closure passed to `Isolate.run` captures its *whole*
  enclosing scope; if that scope holds a `DynamicLibrary`/`Pointer`, sending it
  fails. Build the closure in a small helper function that only sees plain
  values, or use `@Native` top-level functions (preferred: nothing to send).
- Hooks only see a small allowlist of env vars, and `user_defines` are read
  from the **workspace root** pubspec (the app), not from our own pubspec.
- BrainFlow buffers are row-major `double[numRows * numSamples]`; row count
  comes from `get_num_rows(boardId, preset)`. Copy into Dart memory before
  freeing.
- `get_board_data` removes data from the ring buffer; `get_current_board_data`
  does not. Don't mix them up in `BoardSession`.
- Always `releaseSession` (and `releaseAllSessions` on hot restart in debug),
  otherwise the next `prepareSession` for the same board/params fails because
  the session already exists or the port is still open.
- The devcontainer bind-mounts the host D-Bus so BlueZ (and a real headband)
  is reachable from Linux builds; see `.devcontainer/`. In M0 it was not
  reachable (`bluetoothctl` couldn't connect; probably the AppArmor note in
  `devcontainer.json`).

## Implementation plan

Each milestone ends with green analyze + tests and an updated README/CHANGELOG.

**M0 – Spike (done 2026-11-18, code in `spike/`; delete once M1 lands)**
- Linux: synthetic board streamed at 250 Hz via `DynamicLibrary.open` and via
  hook + `@Native`; session prepared in one isolate, read in another
  (state is process-global). BLE path loads bundled `libsimpleble-c.so`.
- Android: debug and release APKs (arm64) package all four libs via the hook.
- Findings are under *Key design decisions* and *Gotchas* above.
- **Still open:** run on a physical Android device (synthetic board, then a
  BLE board such as `MUSE_2_BOARD`) to confirm loading and that SimpleBLE
  finds its bridge classes. Deferred: no Android hardware available yet, so
  Android stays "builds and packages", not "verified on device".

**M1 – Package skeleton and native delivery**
- `flutter create --template=package_ffi` (or equivalent) plus an `android/`
  Gradle part for `simpleble-bridge.jar`; vendored headers, `ffigen.yaml`
  (`ffi-native` with asset ids), `tool/update_brainflow.sh`.
- `hook/build.dart`: download + sha256 check + `lib_dir` user-define override.
  The upstream archives are 118 MB / 100 MB and contain every OS; prefer
  repackaging them per OS/ABI (~5 MB each) into our own GitHub release assets
  via `tool/`, so app builds download only what they need.
- Decide which vendor-SDK helpers to ship on Linux (unicorn, eego, Synchroni,
  ...): check licenses; default to core + BLE (SimpleBLE, Muse, Ganglion,
  BrainBit, BrainFlowBluetooth).
- CI (GitHub Actions, Linux): analyze, unit tests, native tests.

**M2 – Core types + `BoardShim`**
- `core/`: board ids, presets, log levels, exit codes/exception,
  input params, board description, `BoardData`.
- `BoardShim`: prepare/start/stop/release, `getBoardData`,
  `getCurrentBoardData`, `getBoardDataCount`, `insertMarker`, `configBoard`,
  `addStreamer`/`deleteStreamer`, static info getters (sampling rate, channel
  lists, descr), logging, version.

**M3 – `BoardSession` + example app (first usable release, 0.1.0)**
- Async connect/disconnect, polling interval config, `Stream<BoardData>`,
  state (`disconnected/connecting/ready/streaming`), proper disposal.
- Example: pick board, connect, live EEG plot with the synthetic board.

**M4 – `DataFilter`**
- Filters (band-pass/stop, low/high-pass, environmental noise), detrend,
  denoising, FFT/PSD (Welch), band powers, downsampling, file read/write.
  Functions that mutate in place take/return `Float64List`.

**M5 – `MLModel`** — prepare/predict/release with metrics and classifiers.

**M6 – Polish & publish**
- More platforms (macOS/Windows), API docs, pub.dev score, versioning that
  tracks BrainFlow (`<ourVersion>+bf<brainflowVersion>` in CHANGELOG).
